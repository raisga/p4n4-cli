**p4n4 0.4.1** creates the shared `p4n4-net` network on the subnet the project asks for, so a project starts where another network already holds the default range.

```bash
pipx install p4n4==0.4.1    # or: pip install p4n4==0.4.1 (Python 3.11+)
```

> **Trusted networks only.** p4n4 0.4.x is meant for development and trusted local networks. Don't expose its service ports to the internet or to networks you don't control.

## Fixes

- **`P4N4_SUBNET` is honoured:** `p4n4 up`, `p4n4 ai system1 enable` and the n8n credential sync created `p4n4-net` on `172.20.0.0/16` whatever the project's `.env` said. Where a VPN or another Compose project held that range, they failed with "Could not create the p4n4-net network", even with `P4N4_SUBNET` set. They now use the project's value (iot's `.env` first).
- **A clearer error:** when the range is taken, the error says so and suggests setting `P4N4_SUBNET` to a free range, such as `172.28.0.0/16`.

## Compatibility

- Requires **p4n4-lib 0.4.1** (installed with it).
- Pairs with the same releases as 0.4.0: projects with the dashboard layer pin **p4n4-dashboard 1.3.0**, which pairs with **p4n4-api 0.3.0**.

## Upgrading from 0.4.0

- Nothing to change. If you created `p4n4-net` by hand to work around this, it keeps working; `docker network inspect p4n4-net` shows its subnet.
